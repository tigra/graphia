## Slicing rationale (read before reordering)

**Why the write path is Slice 1, ahead of the feature.** Every later slice writes the ledger more often — ten times a run instead of once. Making the write atomic *first* means the increase in write frequency lands on a safe primitive. Do it the other way round and Slice 3 multiplies today's corruption window (`append_record` at `blunder_eval.py:3256`–`3259` performs **two unsynced writes**, and a multi-kilobyte buffered write is far above `PIPE_BUF`) by ten. Slice 1 is also the only slice that improves the *existing* behaviour without changing it: after it, `persona_bench`'s single end-of-run write is atomic too, for free.

**Why run identity is its own slice, before the progressive write.** The upsert in Slice 3 recognises its own document by id, and `make_run_id` (`:3279`) is a local timestamp to the **second** — two runs launched in the same second share an id, which this project has done. Landing the id first means Slice 3's splice never has a window where it can pick the wrong document, and the id ships on records even if Slice 3 were deferred.

**Why the scoring extraction is a task inside Slice 3 and not a slice of its own.** Moving `:4413`–`:4587` into a callable delivers no capability by itself; as a lone slice it would be a horizontal refactor. It is Task 3.1, and its verification is the strongest regression this spec has: a complete run's record must be **byte-identical** to today's.

**Why the early-stop marker is Slice 4 and not Slice 3.** Slice 3 already satisfies the functional spec's durability requirement — a killed run leaves a record. Slice 4 is what stops that record being *misread* as a planned run of that size. They fail independently, they are verified differently (one by a kill, one by a rendered key), and Slice 3 is useful shipped alone.

**Why the viewer is in scope at all, given §3 puts presentation out of scope.** `eval_ledger.py:2999` renders the `Games` column from the number **requested**. That cell is correct on all 50 committed records; Slice 4 is what makes it lie. The spec that introduces an ambiguity into an existing display owes the fix — this is repair, not the presentation work the functional spec deferred. See technical-considerations §2.6.

**Why documentation is a slice and not a trailing chore.** `evals/README.md` opens with **"Append-only. … A run never overwrites or rewrites an earlier record"** and restates it at line 923. This spec makes that false as written. A reader who trusts the contract over the code is the failure mode, and the contract is the artifact other specs cite.

**Why the cost measurement is last, and is not optional.** Re-scoring per game makes `score_repetition` — pairwise over all pooled AI lines — run *N* times over a growing pool. Technical-considerations §2.8 requires this **measured on a real ten-game run, not assumed**; it can only be measured once everything else is in place.

## Slice 1: The ledger write becomes atomic, with no change to what it writes

**Value:** a run killed mid-write can no longer truncate the ledger or leave a `---` separator with no document behind it. Today that is a live hazard on every record; after this slice it is closed by construction. Nothing about the record's content, key order or byte layout changes — `persona_bench` and the eval harness keep their single end-of-run write and gain atomicity without touching their call sites.

**VERIFIED 2026-09-11 (Task 1.5).** The "no change to what it writes" claim is a measurement, not a promise: the pre-change append-mode writer and the new atomic one were run side by side out of two source trees differing in exactly one file, over a **38-case matrix** — five record shapes (a `notes` containing `---`, a multi-line block scalar, an empty `notes`, the value-type `mean`/`peak` float facets, and a `persona_bench` record built through the real `build_bench_record`) against seven ledger states (missing, empty, the committed 50-record file, preamble-only, no trailing newline, CRLF, four-dashes), plus the no-arg `LEDGER_PATH` path and two sequential-append runs. **38 identical, 0 differ.** On the committed-ledger cases the original 171,686 bytes are an exact *prefix* of the result and `safe_load_all` goes 50 → 51. Not a byte difference, so Slice 1's claim stands. The load-bearing half was confirmed working: on an **existing** target the mode is carried across (`0644` → `0644`). Confirmed it cannot dirty the tree — git records both `0600` and `0644` as `100644`. Exposure is nil today (the committed ledger exists; a `--ledger-path` scratch file is read by the same user), but Task 3.2 should know it is inheriting this and not rediscover it.

## Slice 2: Every new record carries a collision-proof run id

**Value:** a record can be found by the run that wrote it, and two runs launched in the same second can no longer be confused for one another. Visible immediately in the YAML as `run.id`, and it remains the transcript directory's name so the by-eye cross-reference a reader makes keeps working.

**WIDTH DECIDED 2026-09-11, and it diverges from §2.2's illustration — six hex characters, not four.** The example in technical-considerations §2.2 (`2026-09-10T13-31-38-a7f3`) fixes the *shape* and leaves the width to implementation; the width landed at six because of what a collision actually does, which is worse than it first looks. §2.1's read-back does **not** catch one: step 3 replaces *the chunk carrying this run's id*, so a colliding run B writes over run A's document, and step 6's *exactly one chunk carries this run's id* then finds B's own chunk and **passes**. A's record is gone with no exception, no fallback file, and nothing in either run's output mentioning it — the loss is visible only as a record that used to be in the ledger and no longer is. Sizing follows from that consequence rather than from the probability alone: ≈6·10⁻⁸ per same-second pair at 24 bits against ≈1.5·10⁻⁵ at 16, for two characters of directory name. Two further choices are load-bearing and argued at the function: **lowercase hex only**, because macOS's default APFS is case-insensitive and a mixed-case suffix could let two *distinct* ids name one directory — reintroducing the very failure through the alphabet; and **`secrets` rather than the module-global `random`**, not for unpredictability but because this module *seeds* that stream (`_seed_game` calls `random.seed(base_seed + game_index)`), so two same-second runs sharing a `--seed` would share a suffix. It is safe today only by call ordering, which is the kind of safety that breaks silently when code moves.

## Slice 3: A stopped run leaves the games it finished

> **READ THIS BEFORE §2.2 — two claims there are stale, and Slice 3 builds the upsert straight off that section.** (a) *"It stays the same string as the transcript directory name"* is true of a **game** record only. A `persona-bench` record carries an `id` and **no** `transcript_dir` (Task 2.2b), so an upsert that located a document by `transcript_dir` would find nothing on that path. Match on `run.id`, never on the directory. (b) §2.2 illustrates the id as `…-a7f3`, a **four**-character tail; the implementation uses **six** — see the WIDTH DECIDED note above Slice 2 for why. Neither correction is in the tech spec itself: the spec is the author's, and these live here.
>
> **`run.seq` is IN, decided 2026-09-11.** §2.2 offers it as *"optional, and recommended for diagnosability: a per-run write counter, incremented on each update"*, and no task owned it — meaning it would have been dropped silently rather than declined. It earns its place against this mechanism's one residual failure: two writers both pass the hash check, replace in sequence, and the loser's newest update is rolled back a generation with **nothing raised anywhere**. Without a counter, "which write won" is unanswerable after the fact; with it, a record whose `seq` went backwards is a visible fact. Additive, gated like the marker, no `METRICS_VERSION` bump.


**Value:** the defect this spec exists for is gone. A run asked for ten games and killed after four leaves **one** record covering exactly those four games — because the record was already written, not because anything noticed the kill. This is the slice that makes five and a half hours of local-model work survivable.

**VERIFIED ON A REAL RUN 2026-09-12 (Task 3.7).** Two Nova games against `4ff09b1`, 6m46s wall clock / `duration_seconds: 404.346`, watched by a re-reading poller armed before launch. Three writes, `run.seq` **1 → 2 → 3** exactly as predicted from the one-game run's `seq: 2`, `games_completed` 1 → 2 → 2, and **one document at every observation**. The completeness argument is stronger than sampling: `seq` increments once per `upsert_record` call and went up with no gaps, so the three observed states are *every* write the run made — there was no unobserved moment to miss. `ended_early` absent throughout (it finished what it asked for), the balance invariant holds, `"Appended one record to …"` printed exactly once, and no `.tmp` litter or fallback file was left behind.

**Three documented behaviours were witnessed rather than argued.** The three writes produced three **distinct inodes** (37144192 → 37145142 → 37145157), so the `tail -f` caveat is now an observation: a descriptor-following reader would have sat on the first inode showing a one-game record forever. The scratch ledger landed at `-rw-------`, the Slice 1 brand-new-file case Task 3.2 was warned it inherits. And `_backup_ledger` left **no directory at all** rather than an empty one — the `not ledger_path.exists()` return precedes the `mkdir`.

**The record got 8 bytes SHORTER between game 1 and game 2** (2914 → 2906). Harmless — rates and Wilson bands re-derive against a growing denominator — but it is the concrete instance of the *"a live run's record is not value-stable"* consequence that **Task 6.1 must document**, and a reader expecting a record to grow monotonically would misread it. Use this example there.

**First §2.8 datum, with its caveats.** Per-game wall clock went *down* (202.2 s/game against the one-game run's 225.1 s), so no re-scoring penalty is visible at n=2. The sharper number: `duration_seconds` is stamped at the end of `_finalise_result`, so the **seq2→seq3 gap of 4.102 s** covers write #2 plus one complete finalise pass over the full 200-line pool — **1.01% of the run**. Two cautions carried to Task 7.1: that window also contains a write cycle, so 4.1 s is an *upper bound* on the pass; and `score_repetition` is pairwise, so a 902-line ten-game pool is ~20× the quadratic work per pass with the run total going as the sum of squares. **Cheap at two games is not evidence that ten games is cheap** — which is precisely why §2.8 demands the real measurement.

**THE WINDOW WAS MEASURED, AND THE ESTIMATE THAT MOTIVATED THE TASK WAS WRONG BY TWO ORDERS OF MAGNITUDE (Task 3.8, 2026-09-12).** The change was pitched on the belief that the pre-rename span contained a temp write plus an `fsync` costing *milliseconds*. On macOS/APFS a 172 KB write plus `fsync` costs ~250 µs. Measured, both arms interleaved in one process over 40 writes each on a copy of the real 171,686-byte ledger: **median 466 µs → 215 µs, a 2.17× reduction**, not the ~1000× anticipated. The tail improved more than the median — p90 **599 → 234 µs**, max **1057 → 251 µs** — because the variance that went away *is* the temp write and the `fsync`.

**And the residual window is now dominated by the check, not the rename:** sha256 over the whole ledger is **111 µs** against a **90 µs** rename. A further ~2× is available — the same predicate as a direct `str` comparison against the text step 2 already holds costs **7 µs**, taking the window to ~100 µs — and was **deliberately not taken**, because the content hash is what ADR 014 §3 and §2.1 step 2 name as the version token, and 104 µs is not a reason to diverge from the written cycle without the author. Recorded with its numbers in `_ledger_digest`'s docstring so it is a decision rather than an oversight.
