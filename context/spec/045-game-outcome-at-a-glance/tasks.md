## How these slices are sliced

Each slice leaves `make view-ledger` runnable and changes something a reviewer can see in the Games panel. The ordering is **information first, then the marking of it**: Slice 1 puts all three numbers on every row as plain text, which is the bulk of the value and all of the risk in the parsing; Slice 2 makes the winner stand out, which is where the two measured traps live; Slice 3 labels the columns. Nothing is derived in one slice and displayed in a later one — the winner is parsed in Slice 1 because the strongest test of the whole derivation needs it (the ledger oracle), and it simply is not *marked* until Slice 2.

**The row is segmented from the start.** Slice 1 builds the row as a `Horizontal` of four class-carrying `Label`s even though no colour rule exists yet, so the test helper that reads panel rows changes **once**, not twice. Slice 2 then adds only CSS.

**Two standing rules for every slice.**

1. `tests/test_ledger_viewer.py::test_details_pane_width_is_identical_with_and_without_transcripts` and `::test_panel_width_is_fixed_not_derived_from_its_content` must stay **byte-identical and green**. They are functional spec §2.1's last criterion's witnesses. If a slice makes either fail, the design is wrong, not the test.
2. **No new corpus-count literal** goes into code or tests. Every count-shaped assertion stays relative (`== len(_TRANSCRIPTS)`, not `== 583`), following `tests/test_transcript_highlight.py`'s convention. A live backlog item records ~70 lines that already rot this way; this spec must not add the 71st.

**Verification tooling.** No browser MCP, and none is needed — this is a terminal UI, and Textual's `App.run_test()` + `Pilot` *is* the real-tool harness every one of the 116 existing tests in `tests/test_ledger_viewer.py` uses. Colour and weight claims are verified by reading back resolved per-cell styles with `Screen.get_style_at` and scoring them with the WCAG relative-luminance formula, which is how every number in the tech spec was obtained. The committed corpus under `evals/transcripts/` is read-only throughout. Nothing needs installing.

**If implementation runs in a git worktree** (the author's standing preference for spec work), use `env -u VIRTUAL_ENV uv run …` and never `uv run --active` — spec 044's Task 3.1 found that an inherited `VIRTUAL_ENV` re-points the *main* checkout's editable install at the worktree's `src/`, silently making a concurrent session run this branch's code.

## Slice 2 — The winning side stands out

*Runnable result: on every ordinary row the winning side's count is in its side colour and bold, and the losing side's is dimmed — the same red and blue a reviewer meets inside the game they are about to open. On the row the reviewer is currently sitting on, where the list paints its own blue mark, the colours give way and the winner is picked out by weight alone. The signal degrades from two marks to one, never to none.*

Covers §2.2 (all 8) — 8 of 29.

- [x] **Slice 2: The winning side stands out**
  - [x] 2.1 Add the ordinary-row colour rules to `DetailScreen.DEFAULT_CSS`: the winning side's cell takes `$text-error` (Mafia) or `$text-primary` (Law-abiding) **plus `text-style: bold`**, the losing side's and the separator take `$text-muted`, the prefix takes `$text`. These are the two side colours spec 038 chose, and it chose them because they were the **only** pair clearing 4.5:1 WCAG AA on both builtin themes — so a reviewer who opens a game finds the highlighted side's spoken lines in the same colour. Measured with these rules: dark 5.61:1 winner / 6.28:1 loser, light 8.97:1 / 4.97:1. **[Agent: textual-tui]**
  - [x] 2.2 Add the highlighted-row overrides, keeping Textual's blue mark exactly as it is. Every segment takes `$block-cursor-foreground`; the winner's keeps `bold`; **every non-winner segment must clear it explicitly**, and the rules must be written in **both** the plain `#transcript-panel-list > ListItem.-highlight …` and the `#transcript-panel-list:focus > ListItem.-highlight …` forms. Two traps, both measured, both of which ship looking correct: (i) Textual's own `.-highlight` rule sets `text-style: $block-cursor-text-style`, which is **bold on the whole row** — a first pass had every cell bold and read as working because the winner *was* bold, so weight discriminated nothing; (ii) `$text-muted` is `auto 60%`, a **blend against the cell's own background rather than a colour**, so it re-resolves on the accent blue and in the measured run beat the override on selector specificity, leaving the losing count at **2.57:1**. The dim cell therefore needs an explicit colour in the override. Measured target, all four states: winner bold at 3.78:1 (dark focused), 9.59:1 (dark blurred), 7.83:1 (light focused), 7.73:1 (light blurred). **[Agent: textual-tui]**
