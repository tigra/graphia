> **Verification is headless `pytest` only.** The tokenizer is a pure function, so most of the work is verified without a terminal at all; the UI half goes through Textual's `App.run_test()` harness — the project's established convention in `tests/test_ledger_viewer.py`. **No browser or external MCP is needed and none is missing.** Nothing here reaches a model, the network, or the ledger.

> **Facts already verified against the source and the committed corpus** — do not re-derive, but do not contradict either. The corpus under `evals/transcripts/` holds **298** files: **268** in the spec-022 form (`<player name="…" role="…">`) and **30** pre-022 (indented `Name — Role`). `<vote …>` appears in **264** of them and `<thought player="…">` in **216** — **absence is normal, not corruption**. `Moderator: A new game begins. Welcome, <name>.` and `(no persona recorded)` each appear in **all 298**. **No transcript contains a `[` today** — which is exactly why `markup=False` must stay: persona prose is model-generated and the next one may.

> **Ratified during Slice 1 — the marker vocabulary is TWELVE tags, not the eight the task text lists.** The eight enumerated (`<transcript>`, `<setup>`, `<preamble>`, `<night>`, `<day>`, `<round>`, `<endgame>`, `<kill>`) are the *attribute-free, content-free* subset; `<player …>`, `<vote …>`, `<recap>` and `<thought …>` are markers too, from Slice 1 onward. The tech spec is only self-consistent this way: its `attr` row defines `attr` as the values "inside a **marker**", and Slice 3 requires a thought's "surrounding tag **stays** `marker`". Had those four been `plain` in Slice 1, Slices 2-3 would have to promote whole lines out of `plain` — the rewrite the slicing exists to avoid — and a game would render with `<setup>` dimmed while each `<player …>` inside it read as content. **An inline `<tag>content</tag>` yields three spans** (opening `marker`, content, closing `marker`), except `<kill>` whose content is also `marker` and therefore coalesces back to one span. Do not write a test asserting `<player …>` is `plain`.

> **Ratified during Slice 1 — how a kind becomes an appearance, for every later slice's styling task.** The kind → style map is `_TRANSCRIPT_KIND_COMPONENTS` in `src/graphia/ui/ledger_viewer.py`: `kind → Textual component-class name`, one CSS rule per entry in `TranscriptScreen.DEFAULT_CSS`, resolved to Rich styles by `TranscriptScreen._kind_styles`. Adding a kind is one dict entry plus one rule. **Two traps, both measured on the installed Textual 8.2.4, not inferred:** (1) `get_component_rich_style(name, partial=True)` returns the rule's properties *unresolved* — `$text-muted` comes back `#ffffff` instead of the `#a0a0a0` the same rule renders — so the **full** style is required and its baked-in background is stripped afterwards (`without_color + Style.from_color(color)`); (2) a kind absent from the map appends with `style=None`, i.e. renders unstyled and never raises, which is why `plain` needs no entry. Under the `textual-ansi` theme `$text-muted` and `$text` resolve to the terminal default, so **`marker`** is legible but not distinguishable there — a known, accepted degradation of that one theme. **Narrowed in Slice 2:** this is NOT true of every variable — `$text-secondary` resolves to a concrete `#56abab` even there, and `text-style: bold` survives on every theme, so `attr` (weight) and `field-label` (weight + cyan) stay distinguishable under `textual-ansi`.

> **Slice 1 writes the corpus round-trip property test first.** It is the cheapest exhaustive test in the spec: read-only over 298 real files, no fixtures to author, and it covers both formats and every element-presence combination the corpus actually contains. It makes *"the stored game is never altered"* (functional-spec §2) structurally true rather than merely intended.

## Notes for the implementer

- **A slice goes red in the middle, and that is correct.** Where a slice changes behaviour Slice 1 already pinned, the tokenizer task and the test-update task are **one edit split across two agents** — the tokenizer lands first and the old assertions fail until the slice's test task supersedes them. **The done-criterion "suite green" applies to the SLICE, not to each task inside it.** A mid-slice agent must never weaken or edit an existing test to go green; it reports exactly which assertions its change supersedes and why, and the slice's test task updates them. (Slice 2's tokenizer task left 17 such failures and handed over a precise list — that is the expected shape, not a defect.)
- **Ratified in Slice 2 — three carry-forwards the later slices need:**
  - **Priority ordering in `_line_spans` is now load-bearing.** `Personality: brisk` is shaped exactly like a player named "Personality" speaking, so **Slice 3's `Name:` speaker rule MUST be inserted after the field-label branch** or it steals all 6,200 label lines. Noted in the code too.
  - **`attr` is the value only** — `<player name="Avery" role="Mafia">` yields `marker`/`attr`/`marker`/`attr`/`marker`, with `name="`, the quotes and the tag punctuation staying `marker`. An attribute-free marker stays a single span. Slice 4 re-kinds the `<thought player="X">` owner name from `attr` to a side kind and should not re-derive this boundary.
  - **Slice 5's `human="true"` is deliberately NOT in the tokenizer's `_ATTR_NAMES` whitelist**, so it stays inside the surrounding `marker` span — a machine flag is not a "specific a reviewer reads". Slice 5 should know this rather than discover it.
- **Ratified in Slice 2 — the side palette for Slice 4 is FORCED, and red/green is not available.** Measured independently on the installed Textual against both builtin themes' real backgrounds, only these clear the 4.5:1 AA floor on **both**: `$text` 14.19/12.77, `$text-primary` 7.03/10.69, `$text-muted` 7.16/5.31, `$text-error` 6.34/7.29, `$text-secondary` 4.67/6.39. **`$text-accent` (3.27) and `$text-success` (3.77) fail on `textual-light`** — so the obvious Mafia-red / Law-abiding-green pairing is out, since functional-spec §2 requires legibility on both terminals. `$text` is body/`plain`, `$text-muted` is `marker`, `$text-secondary` is `field-label`. **Slice 4 therefore uses `$text-error` (red) for Mafia and `$text-primary` (blue) for Law-abiding** — the only AA-on-both pair left, and colourblind-safe where red/green is the classic failure. Do not substitute a green.
- **`attr` is achromatic on purpose, and Slice 4 must keep it that way.** From Slice 4 onward **colour means side**. A bare `name=` value carries no side of its own, so tinting it with a surviving hue would render a Mafioso's name in the Law-abiding colour. `attr` lifts by brightness + weight instead. `text-style` survives `_kind_styles`' `without_color + Style.from_color(...)` (verified), so weight composes with colour inside one component class — which is also what keeps Slice 5's bold-within-the-side-colour a one-rule change.
- **Ratified in Slice 3's styling task — the four kinds are separated on `text-style`, not hue, and two of the four rules are PERMANENT.** With `$text`, `$text-muted` and `$text-secondary` already spent and `$text-primary` / `$text-error` reserved for Slice 4, there was no unspent AA-on-both hue, so the axis is `text-style` (which, unlike colour, also survives `textual-ansi`). `thought` = `$text-muted` + **italic** — two axes deliberately, because a terminal without italic support still separates it by brightness and `textual-ansi` (where `$text-muted` collapses to the terminal default) still separates it by slant; on one axis alone the functional spec's "can *never* be mistaken for something said aloud" would quietly fail on real setups. `recap` = `$text` + **reverse** — the only achromatic treatment that changes the text's *mass* rather than its texture, which is what "usable as a scroll landmark" actually requires (bold prose still reads as prose at scrolling speed). Both are permanent: **Slice 4 must not re-kind a thought's body or a recap** — it gives the thought's *owner name* a side (the `attr` span), never the body, and the moderator has no side at all.
- **Ratified in Slice 3's styling task — `speaker`/`speech` are neutral placeholders carrying NO weight, and Slice 4 overrides them by ADDING, never editing.** Both are `color: $text` and nothing else — measured as a visual no-op against the unstyled body (identical `#e0e0e0` on `textual-dark` and identical terminal-default on `textual-ansi`; 2/255 apart on `textual-light`, since `$text` is `auto 87%` where the widget default is `$foreground`). Slice 4 appends its side-bearing kinds to `_TRANSCRIPT_KIND_COMPONENTS` with their own component classes and their own rules and **leaves these two rules alone** — they survive as the correct appearance for a line whose side is unknown (a pre-022 game, or a name absent from the cast list), so "never guess a side" and "the neutral is the body colour" become the same rule. **Slice 4's side rules must set `color:` only, no `text-style`.** That is what keeps Slice 5 possible: functional-spec §2 says other same-side players' lines are "the same colour but **not bold**", so bold on `speaker` would have made that criterion unsatisfiable. Bold is used elsewhere in the stylesheet (`attr`, `field-label`) but nowhere on *a player's line*, so inside dialogue bold is unspent and means exactly one thing — the reviewer's own seat.
- **Ratified in Slice 3 — a ballot is `speaker` + `speech`, not its own kind.** Spec 022 strips the `Moderator:` voice off ballots precisely so `Bo: Yes` reads as the player's own word, and from Slice 4 colour means side — so a vote block then shows at a glance that both Mafiosos voted No, which is the most useful thing colour can say about a vote. A separate achromatic `ballot` kind would throw that away, and telling one apart needs to know the line sits inside `<vote>`, which this deliberately per-line, stateless tokenizer does not.
- **Ratified in Slice 3 — the colon belongs to `speaker`, the separating space to `speech`.** `Avery: hi` → `('Avery:', speaker)`, `(' hi', speech)`. This matches the field-label precedent (`Personality:` is the label, `' brisk'` is the remainder), so the file holds one convention rather than two. Neither spec document constrained this — it is a resolution, not a pin.
- **The speaker rule is shape-driven, NOT cast-list-driven, and tech-spec §2 B is why.** That section fixes pre-022 degradation as "a pre-022 file still gets `marker`, **`speaker`**, **`speech`**, `field-label` and `plain` spans" — and those 30 files have no `<player>` tag at all, so a cast-list-gated rule would silently drop every speaker prefix in them. The split: *side* is a judgement about a name and must never be guessed (Slice 4, from `<setup>`); *"somebody is speaking"* is a shape. Measured over all 298 files the rule captures 22,508 lines under 498 distinct names, and **not one name absent from its own file's cast list** — zero false positives on real data.
- **Casing is NOT a speaker guard, by measurement.** An initial-capital rule was drafted and rejected: **39 corpus cast names are lowercase** (`mina`, `arthur`, `kai`, `zara`, …) and casing would lose **426 real speaker lines** to exclude three literals. The exclusion set is writer vocabulary instead — `Moderator`, `tally`, `outcome` — the same posture as `_FIELD_LABELS` and `_MARKER_TAGS`. The accepted price: a lowercase `personality: brisk` now reads as speech. The real cast-list labels are always capitalised, so the 6,200 `field-label` spans are untouched (verified: count identical across Slices 2 and 3).
- **Ratified in Slice 3 — `speaker`/`speech` are a NEUTRAL PLACEHOLDER that Slice 4 overrides additively.** Both currently take `color: $text` (the body colour). Slice 4 appends side-bearing kinds with their own component classes and rules and **edits neither existing rule**, so `speaker`/`speech` survive as the appearance of a line whose side is *unknown* — a pre-022 game, or a name absent from `<setup>`. "Never guess a side" and "the neutral is the body colour" then become the same rule, so the fallback needs no separate design. **Slice 4's side rules must set `color:` only, no `text-style`.**
- **Ratified in Slice 3 — bold is unspent within dialogue, deliberately, because Slice 5 needs it.** Functional-spec §2 states the contrast literally: the human seat is bold while other same-side players' lines are "the same colour but **not bold**". Spending bold on `speaker` would have made that criterion *unsatisfiable*. `thought` uses muted + **italic** (two axes, because a terminal without italic drops the slant and `textual-ansi` drops the brightness — each covers the other's failure); `recap` uses **reverse**, because a scroll landmark must survive being skimmed, where the eye catches mass rather than texture. Verified: `italic` and `reverse` both survive `_kind_styles` and all three themes, and being SGR attributes they survive `textual-ansi` where `$text` and `$text-muted` collapse to the terminal default.
- **Slice 4 must NOT side-tint a thought's body or a recap.** Tinting a private reflection would claim it is an act of allegiance, and would make thought and speech share a colour; the moderator has no side. The thought's *owner name* is an `attr` span and does take a side colour — that is functional-spec §2's explicit requirement.
- **Ratified in Slice 4 — the unknown-side fallback is the NEUTRAL `speaker`/`speech`, never the `plain` kind.** Slice 4's task text and tech-spec §2 A both say a name absent from the cast list "yields `plain`"; that wording predates `speech` existing as a kind, and it contradicts tech-spec §2 B, which promises pre-022 files keep `marker`, **`speaker`**, **`speech`**, `field-label` and `plain` spans. Task 2's own sentence settles it: *"its speech falls back to `plain` while **speaker prefixes still work**"* is self-refuting if `plain` means the kind. It means *plain-looking* — uncoloured. **What "never a guess" forbids is assigning a SIDE, not styling the line as speech.** Measured: exactly the 30 pre-022 files yield an empty side map, and every one of the 1,853 remaining neutral `speaker` spans is inside them.
- **Ratified in Slice 4 — the side colour lands on whichever token tells the reviewer the side: the ROLE where a role is written, the NAME where none is.** Concretely, only two of the five whitelisted attributes go side-bearing — `<player role=…>` and `<thought player=…>`. A cast entry's `name=` and a vote's `initiator`/`target` stay achromatic `attr`. Tinting every name would leave `attr` with **zero occupants in any real transcript**, retiring Slice 2's achromatic-bold treatment by accident; this way `attr` keeps 3,970 corpus spans. Wherever a name sits beside its own role the role takes the colour, so the two treatments never compete on one line.
- **Ratified in Slice 4 — three "never guess" guards in the side map, each load-bearing:** the map is **scoped to `<setup>`** (a `<player name="Bo" role="Mafia">` typed into a Day speech must not recolour the real Bo — verified it does not); role labels are a **whitelist** mirroring `eval_transcript._ROLE_LABELS`, because the writer's own fallback lets an unmapped role reach the file as a raw string; and a name the cast list gives **two different sides is dropped entirely**, not resolved first-wins.
- **The tokenizer is no longer purely per-line — `_line_spans` is not a function of the line alone.** `tokenize_transcript` makes two passes: `_cast_side_map(lines)` builds a read-only `name → side` dict, then the per-line loop runs with it threaded through. Everything else is preserved (pure, no I/O, no Rich/Textual, never raises, round trip, single coalescing exit, speaker-below-field-label). **Consequence for every later test: the same line tokenizes differently in two different files** — a synthetic test wanting a side kind must include the `<setup>` block that grants it.
- **Ratified in Slice 4's styling task — the palette is now FULLY SPENT, and the two sides are `$text-error` (Mafia) / `$text-primary` (Law-abiding).** Re-measured on the installed Textual against both builtin themes' real backgrounds, confirming the Slice 2 figures exactly: Mafia **6.34 dark / 7.29 light**, Law-abiding **7.03 dark / 10.69 light** — both clear AA on both. Six rules, not two. **Under `textual-ansi` both resolve to CONCRETE colours** (`#ab5656` / `#5656ab`) rather than collapsing to the terminal default the way `marker`'s and `thought`'s `$text-muted` does, so the sides survive all three builtin themes — the same behaviour Slice 2 found for `field-label`. No AA figure is quotable for `textual-ansi` (the background is the terminal's own). **Nothing is left over**: a later kind that needs to be *seen* must reach for `text-style`, as Slice 3 did and as Slice 5's bold does.
- **Ratified in Slice 4's styling task — the four DIALOGUE side rules set `color:` only; the two `attr` side rules KEEP `attr`'s bold.** The "no `text-style` on a side rule" constraint was argued to leave bold unspent on *a player's line* for Slice 5, and an `attr` span is not a player's line — it lives inside `<…>` punctuation (a cast entry's `role=`, a `<thought player=…>` owner), never on a line of speech, so the two never share a context and **Slice 5's bold-on-a-line stays unambiguously "the reviewer's seat"**. Dropping the weight would also invert Slice 2's requirement on the very line where it matters most: in `<player name="Avery" role="Mafioso">` the name is bold achromatic `attr` and the role sits beside it, so an unweighted role would read *lighter* than the name it qualifies. Keeping bold makes the two `attr` treatments differ on **hue alone** — same job, now with a side.
- **Known and previously accepted — `field-label` and the Law-abiding side share a hue (205-206°).** On `textual-dark` `#5684a5` vs `#57a5e2`, on `textual-light` `#004f8b` vs `#002d4f`; they separate on brightness/saturation, not hue. Unavoidable inside the forced palette (`$text-primary` is the last AA-on-both hue and `$text-secondary` was already spent), and Slice 2 accepted it in advance: *"a label is never a person, so it cannot be misread as an allegiance even if a side later shares its hue."* They also never sit on one line — the role blue is inside a grey `<player …>` marker, the label blue at the start of a prose line — and field labels occur only inside `<setup>`. Do not "fix" it by re-hueing either rule; there is no unspent hue to move to.
- **The two side hues separate by 140° of HUE, not by luminance** (346° vs 206°; luminance ratio only 1.11 dark / 1.47 light). That is correct and not a defect: the AA figures that matter are each hue against the **background**, which is what functional-spec §2 requires, and telling two coloured texts apart is a hue task. It is also why the forced red/blue pair is *better* than the unavailable red/green — red/blue is the axis every common colour-vision deficiency preserves.
- **Span totals are conserved across Slice 4: 193,740, identical to Slice 3 — only kinds moved, no boundary did.** `attr` 3,970 + `attr-mafia` 3,695 + `attr-law-abiding` 6,448 = 14,113; `speaker` 1,853 + 7,173 + 13,482 = 22,508 (same for speech); `marker`, `field-label`, `thought`, `recap` untouched. A later slice should expect the same conservation and treat a changed total as a boundary bug.
- **A passing sweep can silently lose most of its coverage — found in Slice 4.** When Slice 4 split `speaker`/`attr` into side-bearing forms, the corpus sweep's `elif` chain kept comparing against the neutral literals, so it **stopped seeing 20,655 of 22,508 speaker spans and 10,143 of 14,113 attribute values** while only three of its assertions went red. A sweep that classifies by kind must be widened whenever a kind splits — build its branches from *kind-family tuples* (`_SPEAKER_KINDS`, `_ATTR_KINDS`, …), never from single constants. **Slice 5 splits kinds again; check this.**
- **Two of Slice 4's rules have ZERO real-data coverage, measured.** `('role', 'attr')` occurs **0** times in the corpus (all 1,960 role values are one of the two known labels) and `('player', 'attr')` occurs **0** times (all 8,183 thought owners appear in their own file's cast list). The unrecognised-role and unknown-owner fallbacks exist **only** in synthetic tests — a `KeyError` mutant is caught solely because those synthetic inputs carry no `<setup>`. **Slice 5 adds another map-driven inference; assume its fallback likewise has no real-data coverage and pin it synthetically.**
- **The conservation guard is a relation, not a total, and that is why it survives corpus growth.** `test_the_side_map_moves_kinds_and_never_a_boundary` tokenizes every game twice — once normally, once with `_cast_side_map` stubbed to `{}` — and requires identical span *text* in identical order, differing only by the documented side split. Stronger than pinning 193,740 (a boundary that moved while preserving counts still fails), and it sweeps the empty-cast-map degradation over all 298 files instead of the 30 that hit it naturally. Prefer this shape over absolute totals in Slice 5.
- **The corpus round-trip test is necessary but NOT sufficient — proven, not theorised.** Slice 2's mutation pass changed the field-label branch from `.match` to `.search`, which drops the text before the label and **breaks the round-trip invariant in principle** — and the 298-file sweep did not catch it, because no committed transcript contains a mid-line field label. The corpus only covers shapes the corpus happens to contain. That is why the synthetic near-miss cases (`Alice: my Manner: is clipped`, `He said Personality: brisk`) are load-bearing rather than decorative, and why every later slice must add its own near-misses instead of leaning on the sweep.
- **Field labels are matched unscoped, by deliberate choice.** They occur **zero times outside `<setup>`** in all 298 files, so an unscoped rule and a `<setup>`-scoped one are indistinguishable on real data today. Unscoped keeps `_line_spans` per-line and pure; scoping would make the tokenizer stateful. Reversible in ~5 lines, and Slice 4 needs `<setup>` state anyway — revisit there if it turns out to matter.

- **The round-trip invariant is the spine of this spec, not a nicety.** `"".join(text for text, _ in spans) == original`, asserted over all 298 committed transcripts, is what makes the "stored game is never altered" requirement structural. Every slice adds kinds; every slice must leave it passing. A dropped or duplicated character is invisible against a wall of text and would otherwise ship.
- **`markup=False` is not negotiable.** Spans only. The corpus contains no `[` today, but persona prose is model-generated, and the existing comment in `TranscriptScreen.compose` already names this hazard.
- **`$text-muted` is right here and was wrong in spec 037.** It resolves to `auto 60%`, which the CSS parser **rejects** for `border:` — and a screen whose CSS fails to parse never mounts (that mistake cost 15 test failures in 037). This spec sets `color:` only, where it is the module's own precedent.
- **Assert span structure, not rendered colour.** Colour is theme-dependent and a poor test subject; 037 established this. Appearance is reviewed by eye, structure is asserted programmatically.
- **Relative equality alone can be vacuously true (037's mutation finding).** An assertion of the form "X equals Y between two states" can hold while both are broken identically. Where a test compares two tokenizations, also pin absolute expected spans.
- **Absence is normal.** 34 files have no `<vote>`, 82 have no `<thought>`, 30 have no `<player>` tag at all, and — **found in Slice 1** — only **278 of 298** have an `<endgame>` tag: in the pre-022 era the ending is folded inside the trailing `<night>` block instead. Relatedly, **no transcript ends with a newline** (all 298 end on `>`), so a tokenizer that appends a newline per line fails the round trip on every single file. A tokenizer that assumes presence passes its synthetic fixtures and breaks on real data — which is why the corpus test exists.
- **Keep `eval_ledger.py` free of Rich and Textual.** Verified today: zero matches. That is the property which lets the parsing — the part most worth testing — be tested as a pure function with no terminal.
- **Spec 037 is Completed**, so `ledger_viewer.py` is uncontended now; the two specs touch different classes and 037 deliberately left `TranscriptScreen`'s rendering alone for this one.
- **Textual 8.x's native renderable is `Content`**, not Rich's `Text`. A Rich `Text` is **verified working today** — `Static.render()` returns a `Content` with the spans preserved — so use it, but a future refactor may prefer building `Content` directly.

In a **fresh worktree** it is **1282 passed, 8 skipped** — the 7 extra skips are all `test_lambda_zip_contents.py`, which skips when `infra/lambda/.build/*.zip` is absent, and that artifact is gitignored so no fresh checkout has it.
